# 設計判断の記録 (ADR)

新しい判断は末尾に追記する。考えが変わったときは古い項目を消さず、Status を `Superseded by ADR-xxx` にする。

---

## ADR-001: 通知はアプリ内通知 + Web Push で完結させる
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様は Discord Webhook で晒し上げる設計だった。オーナーの要望は「外部ツールは使いたくない、アプリ内で完結させたい」。
- **Decision**: 通知の正本は DB の `notifications`（アプリ内のベル・一覧。Supabase Realtime で即時反映）。アプリを閉じているときは PWA の Web Push（VAPID + `web-push`）で届ける。晒し上げはダッシュボードのタイムラインで行う。
- **Consequences**:
  - iOS で Push を受け取るには **iOS 16.4 以降でホーム画面に追加**する必要がある。オンボーディングで案内する。
  - Push は届くことが保証されない（OS の省電力機能・通知の拒否）。アプリ内通知を正本にして、Push は「おまけ」として扱う。
  - 外部サービスのアカウントは不要。費用も 0 円のまま。

## ADR-002: Gemini のモデルは環境変数で指定する
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様の `gemini-2.0-flash` は 2026-06-01 に提供終了している。無料枠で使えるモデルやレート制限は頻繁に変わる（2026-04 以降、Pro 系は無料枠の対象外）。
- **Decision**: `GEMINI_MODEL` 環境変数でモデル ID を指定する。既定は無料枠のある Flash 系の最新版（実装時に Google AI Studio で ID を確認する）。SDK は `@google/genai`。出力は `responseMimeType: application/json` + `responseSchema` で `{score, feedback}` に固定する。
- **Consequences**: モデルの提供終了はコードを変えずに環境変数の変更だけで対応できる。判定のたびに使ったモデルを `submissions.ai_model` に残す。

## ADR-003: 定期実行は Supabase pg_cron で行う（GitHub Actions は使わない）
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様は GitHub Actions を 15 分ごとに実行する設計だった。
  - private リポジトリの無料枠は月 2,000 分で、ジョブ 1 回ごとに 1 分単位で切り上げて課金される。15 分ごとだと月 ~2,900 回になり、**無料枠を超える**。
  - public リポジトリなら無料だが、スケジュール実行は数十分遅れることがよくあり、60 日間活動がないと自動で無効になる。
  - Vercel Hobby の Cron は 1 日 1 回まで。
- **Decision**: Supabase Free に含まれる `pg_cron` + `pg_net` で、5 分ごとに `POST /api/cron/tick` を呼ぶ。シークレットは Supabase Vault に置く。
- **Consequences**: リポジトリの公開・非公開に関係なく 0 円で動く。tick は冪等に作るので、取りこぼしや重複があっても問題ない。

## ADR-004: 書き込みはサーバーだけが行い、状態遷移は Postgres 関数に集める
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の RLS では、ユーザーが自分の `total_penalty_points` や `status`・`ai_score` を直接書き換えられた。罰ゲームアプリでは改ざんへの耐性が肝になる。
- **Decision**: `authenticated` ロールに許可する書き込みは、プロフィールの表示項目・通知の既読・自分のフォルダへの画像アップロードだけ。それ以外は Server Action / Route Handler が service role で RPC を呼ぶ。RPC は `service_role` だけが実行できる。
- **Consequences**: 検証ロジックが DB に 1 か所だけになり、cron と画面操作で同じルールが使われる。そのぶん SQL の量は増えるので、pgTAP などで RPC のテストを書く。

## ADR-005: ポイントは台帳で管理する
- **Status**: Accepted (2026-10-16)。ADR-008 で 1 行 = 1pt から 1 行 = 任意の額に、ADR-012 で一意制約を `dedupe_key` に変更
- **Decision**: `profiles` にカウンター列を持たせず、`penalties`（`study_log_id` が unique）から集計する。精算済みかどうかは `settlement_id` で判断する。
- **Consequences**: 二重ペナルティは一意制約で防げる。精算でどの失敗が消化されたかも追える。

## ADR-006: 招待コード + サーバー側でユーザーを作成する
- **Status**: Superseded by ADR-025
- **Decision**: Supabase の公開サインアップは OFF。サインアップ用の Server Action で `INVITE_CODE` を定数時間比較し、通ったら `auth.admin.createUser({ email_confirm: true })` で作る。
- **Consequences**: anon key で Auth API を直接呼んでも登録できない。確認メールを送らないので、Supabase 無料枠のメール送信上限の影響も受けない。

## ADR-007: 日付は JST 固定、締切は提出時刻で判定する
- **Status**: Accepted (2026-10-16)
- **Decision**: 学習日は `(now() at time zone 'Asia/Tokyo')::date`。提出の締切判定は `submissions.submitted_at < target_end_time` で行う（AI 判定がいつ終わったかは問わない）。判定待ちの間は cron が `judge_grace_minutes` だけ失敗の確定を待つ。
- **Consequences**: 締切直前に提出した人が、Gemini の遅延のせいで失敗にならない。

## ADR-008: ペナルティは 1pt = 1 円とし、失敗の種類と理由で額を変える
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の設計は「失敗 1 回 = 1pt、3pt ごとに全員へ 500 円」だった。オーナーの要望は「払う金額とポイントを同じにする」「失敗には理由を書かせ、理由によって扱いを変える」。
- **Decision**: 宣言なし 500pt、サボり 700pt、「宣言が妥当じゃなかった」は次の計画を書けば 0pt（4 回連続から 500pt）、「急遽予定・その他」はほかの全員が納得すれば 0pt（1 人でも拒否、または期限内にそろわなければ 500pt）、申告しなければサボり扱い。未達成の後処理は `failure_reports` と `excuse_reviews` で状態を持つ。金額はグループ設定で変えられる。
- **Consequences**:
  - 「未達成」がすぐにペナルティ確定ではなくなるので、未達成 → 申告待ち → 審査中 → 確定、という状態が増える。期限切れは cron が処理する。
  - 全員一致が必要なので、1 人が審査を放置すると承認されない。審査締切の 3 時間前に、まだ押していない人へリマインドを送る。
  - 「宣言が妥当じゃなかった」を選び続ける逃げ道は、連続回数の上限で塞ぐ。

## ADR-009: 精算は月の最終日に、支払先 1 人へまとめて払う
- **Status**: Superseded by ADR-010（時期）・ADR-019（支払先の決め方）
- **Decision**: 月の最終日の 09:00 に、確定済みの未精算ポイントを人ごとに合計して `settlements` を 1 件作る。支払先は本人があらかじめ決めた人（`profiles.payee_id`）で、未設定ならほかのメンバーからランダムに 1 人選ぶ。送金した側が「送金した」、受け取った側が「受け取った」を押して完了。
- **Consequences**: 送金は 1 人あたり月 1 回で済む。審査中のものなど、その時点で確定していないペナルティは翌月に回る。ランダムの結果は記録し、選び直せないようにする。

## ADR-010: 精算は毎週土曜 23:00 に行う
- **Status**: Accepted (2026-10-16)。時刻は ADR-023 で 23:59 に変更
- **Context**: 月 1 回だと、ペナルティから支払いまでが最大 1 か月空き、痛みが薄れる。
- **Decision**: ADR-009 の仕組み（支払先 1 人、未設定ならランダム、送金した / 受け取った）はそのままにして、締めを毎週土曜 23:00 (JST) にする。休息日の上限を数える週も日曜〜土曜にして、精算と区切りを揃える。
- **Consequences**: 送金は 1 人あたり最大で週 1 回になる。土曜当日の未達成は 23:00 の時点では確定していないことが多く、翌週の分に入る。

## ADR-011: 宣言の軽さはメンバーの指摘で防ぐ
- **Status**: Accepted (2026-10-16)
- **Context**: 宣言の中身に基準がないと、「本を 5 分読む」のような軽い宣言で毎日楽に達成できてしまう。AI によるチェックや最低時間の案もあったが、オーナーはメンバーによる指摘を選んだ。
- **Decision**: 宣言から 3 時間以内なら、ほかのメンバーがコメント付きで「軽すぎる」を押せる。押されたら本人は 1 時間以内に書き直す。書き直さなければ宣言なし (P6, 500pt)。指摘は 1 宣言に 1 回。
- **Consequences**: 宣言の変更不可に例外ができるので、書き直す前の宣言を `original_declaration` に残して、全員に見えるようにする。1 人の指摘で書き直しになるので、身内どうしの信頼が前提になる。

## ADR-012: 精算は相殺せず、未払いには毎週ペナルティを足す
- **Status**: Accepted (2026-10-16)
- **Decision**: A→B と B→A がある週も相殺しない。次の精算までに「送金した」になっていなければ P7 (500pt) を足し、払うまで毎週続ける。P7 は学習日と関係ないので、penalties の一意制約を `study_log_id` から `dedupe_key`（`log:{id}` / `late:{settlement}:{週}`）に変える。
- **Consequences**: 判定は「受け取った」ではなく「送金した」で行う（支払先が確認を忘れたせいで P7 が付かないようにするため）。支払先は「届いていない」を押して `open` に戻せる。

## ADR-013: 長い休みは全員の承認で休会にする
- **Status**: Accepted (2026-10-16)。期間の上限と期限は ADR-014 で変更
- **Decision**: 期間と理由を書いて申請し、ほかの全員が承認したら成立する。審査は理由申告の審査と同じ仕組み（1 人でも却下、または期限内にそろわなければ不成立）。その日が始まる前に承認されていた日だけを休会扱いにする。休会中の人は審査者から外す。
- **Consequences**: 「全員一致」の審査に参加する人数が日によって変わるので、審査の行は申請・申告した時点で作って固定する。

## ADR-014: 期限を 5 時間に縮め、通知は双方向・期限の手前にも出す
- **Status**: Accepted (2026-10-16)。理由申告・審査の期限は ADR-017 で「次の宣言締切」に変更
- **Decision**:
  - 1 日の始まりは 0:00 JST に固定する（個人ごとの設定はやめる）。0:00 と 11:00 に未宣言のリマインドを出す。
  - 理由申告と審査（理由・休会）の期限は 5 時間。指摘できるのは宣言から 3 時間、書き直しの期限は 1 時間。
  - 休会の長さに上限は設けない。妥当かどうかはほかのメンバー全員の承認で決める。
  - 通知は「行動した人 → 関係する人」「反応した人 → 行動した人」の両方向に出す。期限があるものは、発生時と期限の手前（残り 1 時間・15 分）に出す。自分の対応が必要な通知は Push を OFF にできない。
- **Consequences**: 期限が短いので、Push が届かないと不利になる。通知を許可していない人には警告を出し続ける。夜間に期限が来る問題が残る（requirements §7 の未決事項）。

## ADR-015: 証拠は「合言葉・開始時の写真・使い回し検出・メンバーの指摘」の 4 重にする
- **Status**: Superseded by ADR-016
- **Context**: 写真 + 振り返り + AI 採点だけだと、昔の写真やネットの画像の使い回しを見抜けず、「今日やった」証明にならない（画像は圧縮で撮影日時の情報が消える）。
- **Decision**:
  - 宣言時にその日だけの**合言葉**を発行し、開始時の写真と提出写真の 1 枚以上に写させる。Gemini が確かめ、写っていなければ不合格。
  - **開始時の写真**で学習中になる。開始していないと提出できない。経過時間は全員に見せ、AI の判定材料にもする。
  - **知覚ハッシュ**をサーバー（`sharp`）で計算し、グループ全員の過去の画像とほぼ同じなら Gemini に送る前に不合格。ハッシュは画像を消しても残す。
  - AI が合格にしても、ほかのメンバーが 3 時間以内に**「怪しい」**を押せる。本人は 1 時間以内に追加の証拠を出せ、全員の納得がなければ P8 (700pt)。
  - 審査が 3 種類（理由・休会・疑義）になったので、審査テーブルを `peer_reviews` 1 つにまとめ、`cast_review` で共通に扱う。
- **Consequences**: 依存に `sharp` が増える（Vercel でそのまま動く）。Gemini の呼び出しは開始時の確認ぶん増えるが、1 日 30 回程度で無料枠に十分収まる。合言葉を紙に書く手間が毎日発生する。

## ADR-016: 証拠は「合言葉 + AI 判定 + メンバーの『怪しい』」にする
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-015 の開始時の写真と知覚ハッシュは、オーナーの判断で不要になった。合言葉はその日にならないと分からないので、昔の画像や他人の画像の使い回しは合言葉だけで防げる。
- **Decision**:
  - 提出写真の 1 枚以上に合言葉を写し、Gemini が探す。合格 = 70 点以上 かつ 合言葉あり。合言葉は全員に見えてよい。
  - 合格の通知から 3 時間、ほかのメンバーは「怪しい」を押せる（複数可）。誰も押さなければそのまま達成で確定。
  - 押されたら、本人は 1 時間以内なら何度でも証拠を送り直せる。指摘した全員が取り下げれば確定。そろわなければメンバーの最終審査になり、理由付きの却下が 1 人でもあれば P8 (200pt)。
  - 宣言から提出までの経過時間は見せるだけ（最低時間なし）。
- **Consequences**: `sharp` と開始時の写真が不要になり、実装が軽くなる。最終審査は「期限までに却下がなければ承認」で、理由申告の審査（期限までに全員の納得がなければ却下）と逆の扱いになる。却下に理由を必須にしたため、黙っていることは却下にならない、という整理。

## ADR-017: 理由申告・審査の期限は「次の宣言締切」にする
- **Status**: Superseded by ADR-022
- **Context**: 5 時間の期限だと、夜中に期限が来て寝ている人が押せずに却下・ペナルティになる抜け穴（不公平）があった。
- **Decision**: 理由申告・理由の審査・休会の審査・「怪しい」の最終審査の期限を、出来事のあとに来る最初の 12:00 にする（残り 6 時間未満なら翌日の 12:00）。発生時・8:00・11:00・11:45 に未対応の人へ通知する。提出締切の上限も翌日 12:00 にする。
- **Consequences**: 期限が必ず昼になり、全員が起きている時間に対応できる。期限の計算は `next_deadline()` にまとめる。

## ADR-018: 通知を ON にしないとアプリを使えなくする
- **Status**: Accepted (2026-10-16)
- **Decision**: 全画面の手前に通知ゲートを置き、ホーム画面追加（iOS）・通知の許可・Push 購読・テスト通知の確認（バナーとサウンド）がそろうまで先へ進めない。開くたびに再確認する。通知の種類ごとの OFF はなくす。
- **Consequences**: OS 側のバナー・サウンドの設定は Web から検出できないので、本人によるテスト通知の確認で代える。

## ADR-019: 支払先はグループで決めて管理者が入力する。最初の週はお試し期間
- **Status**: Accepted (2026-10-16)
- **Decision**: 支払先のランダム選択をやめ、グループで話し合って決めた「誰が誰に払うか」を管理者が入力する。全員分そろうまでお試し期間を終えられない。登録から次の日曜 0:00 まではお試し期間で、ペナルティは記録だけして（`waived = 'trial'`）精算しない。パスワードを忘れたら管理者が仮パスワードを発行する。
- **Consequences**: 途中参加のメンバーにも、それぞれお試し期間が付く。

## ADR-020: 記録は追記だけにして、振り返り機能を持つ
- **Status**: Accepted (2026-10-16)
- **Context**: オーナーの要望は「いつ何を宣言し、何を学び、どれだけ達成できたか、却下された理由まで全部残して振り返りたい」。
- **Decision**:
  - 履歴のテーブルは追記だけにする（DELETE 禁止、UPDATE は状態と時刻の列だけ、をトリガーで強制）。外部キーは cascade しない。抜けたメンバーは `deactivated_at` で無効にするだけ。
  - 写真の原寸は 60 日で消すが、サムネイル（~20KB）は永久に残す。文字の記録はすべて永久。
  - 振り返り画面（カレンダー・1 日のタイムライン・統計・指摘と却下の一覧・次の計画の追跡・検索）と、毎週土曜の週の振り返り（数字 + Gemini の要約 + 本人のメモ）、CSV / JSON の書き出しを作る。
- **Consequences**: 間違ったデータを直すときもマイグレーションで明示的に行うことになる（アプリからは消せない）。DB の容量は数 MB/年、サムネイルは ~45MB/年で、無料枠に何年でも収まる。週の振り返りの Gemini 呼び出しは週 6 回程度増えるだけ。

## ADR-021: 振り返りは表とグラフで見せる（shadcn/ui Chart + TanStack Table）
- **Status**: Accepted (2026-10-16)
- **Decision**: 個人の振り返り（数字のカード・達成カレンダー・達成率・点数・時間・時間帯・ペナルティ・未達成理由・指摘と却下・学習ログの表）と、グループの比較（比較表・グループのカレンダー・達成率の比較・ランキング）を作る。グラフは shadcn/ui の Chart（Recharts）、表は TanStack Table、カレンダーは CSS Grid。集計は DB のビューで行う。
- **Consequences**: どれも無料のライブラリで、追加の費用はない。色は 1 か所で管理し、色だけに頼らず記号とラベルを付ける。

## ADR-022: その日の出来事はその日のうちに決着させる
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-017 の「次の宣言締切（翌日 12:00）」は夜中の期限を避けられるが、オーナーの考えは「その日の振り返りはその日にする」。
- **Decision**: 理由申告は当日 23:00、審査（理由・休会・「怪しい」の最終審査）は当日 23:59 まで。そのぶん時間を残すため、提出締切の上限を当日 21:00、「怪しい」の受付を最長 22:00、送り直しを最長 23:00 にする。期限の計算は `day_at(学習日, 時刻)` にまとめる。「怪しい」の最終審査は、23:59 までに理由付きの却下がなければ達成で確定（オーナー確認済み）。
- **Consequences**: 学習日をまたぐ状態がなくなり、日ごとの記録が 23:59 で必ず確定する（振り返りの集計も単純になる）。夜型の人は提出締切を 21:00 より遅くできない。審査者は夜（22:00〜23:59）に対応する必要がある。

## ADR-023: 精算と週の振り返りは土曜 23:59、その日の決着のあとに行う
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-022 で毎日 23:59 にその日の出来事が決着するようになったが、精算が土曜 23:00 だと土曜の分が翌週に回っていた。
- **Decision**: 精算と週の振り返りを土曜 23:59 にし、同じ tick の中でその日の決着を先に済ませてから行う。
- **Consequences**: 1 週間（日〜土）の出来事がすべてその週の精算に入り、持ち越しがなくなる。実際の処理は日曜 0:00〜0:05 の tick で行われる。お試し期間の終わり（日曜 0:00）とも区切りがそろう。

## ADR-024: 開発はクラウドの Supabase 開発用プロジェクトで行う
- **Status**: Accepted (2026-10-16)。M9 からはこのプロジェクトを本番と共有する（ADR-031）
- **Context**: ローカルの Supabase は Docker で 10 前後のコンテナを動かし、開発機（メモリ 8GB）には重い。
- **Decision**: Supabase の無料プラン（2 プロジェクトまで）で、開発用と本番用のプロジェクトを分ける。開発中は開発用プロジェクトに直接つなぎ、マイグレーションは `supabase db push` で反映する。キーは新形式（publishable / secret）を使う。
- **Consequences**: Docker が不要。オフラインでは開発できない。データを作り直すときは `supabase db reset --linked`（開発用プロジェクトだけに使う）。7 日使わないと一時停止するので、再開してから作業する。pg_cron から開発機の tick は呼べないので、開発中は tick を手動で呼ぶ。

## ADR-025: ログインは Google、メンバーになるには招待コード
- **Status**: Accepted (2026-10-16)。招待コードの部分は ADR-026 で置き換え
- **Context**: メール + パスワードだと、パスワードの管理とリセット（Supabase 無料枠のメール送信上限が厳しい）が手間になる。オーナーの提案で Google ログインにする。
- **Decision**: Supabase Auth の Google プロバイダー（OAuth / OIDC、PKCE）でログインする。Google でログインしただけではメンバーにせず、`/join` で招待コードを入れた人だけに profile を作る（`join_group`）。RLS は `private.is_member()`（profile があり抜けていない）で判定する。
- **Consequences**:
  - パスワードとリセットの仕組みが要らなくなる。費用は 0 円（Google の OAuth クライアントは無料）。
  - 招待コードを知らない人も auth のユーザーとしては登録されるが、何も読めない。
  - Google Cloud での OAuth クライアントの作成と、Supabase での設定が初回だけ必要（README）。
  - iPhone の PWA で OAuth から戻れるかは実機で確認する（M2）。だめならメールのワンタイムコードを予備にする。

## ADR-026: 招待コードはメンバーがその場で発行し、1 回だけ・15 分で使えなくする
- **Status**: Accepted (2026-10-17)
- **Context**: ADR-025 では招待コードが環境変数の 1 つだけで、ずっと同じだった。一度漏れると誰でも参加できてしまい、変えるには管理者がデプロイし直す必要がある。オーナーの提案で「招待したいときにその場で作り、15 分で消える」形にする。
- **Decision**:
  - メンバーなら誰でも招待コードを発行できる。コードは Node の `crypto.randomInt` で作る 10 文字（紛らわしい文字を除いた 31 文字、約 49.5 ビット）。DB（`invites`）には SHA-256 だけを保存し、コードは発行した画面に一度だけ表示する。
  - 1 回だけ使え、`invite_minutes`（既定 15 分）で使えなくなる。期限の判定は DB の `now()`。取り消しの機能は作らない（すぐ切れるため）。
  - `join_group` が、招待の照合（未使用・期限内）・profile の作成・使用済みへの更新を 1 つのトランザクションで行う。advisory lock と `for update` で、同じコードで参加できるのは 1 人だけ。失敗の理由（違う・期限切れ・使用済み）は区別して返さない。
  - メンバーの上限（`max_members`、既定 6）に達したら、発行も参加もできない。
  - 最初の 1 人だけは環境変数 `INVITE_CODE` で参加する。グループが空のときしか通らないので、漏れても実害はほぼない。
  - ログイン前に招待リンクを開いた人のために、戻り先を短命の httpOnly Cookie で `/auth/callback` まで運ぶ（OAuth の戻り先 URL にクエリを付けないので、Supabase の Redirect URLs は `/auth/callback` のままでよい）。
- **Consequences**:
  - 漏れたコードが使えるのは最長 15 分・1 人だけ。誰が誰を招待したかが `invites` と `member_joined` に残る。
  - 相手がすぐに開けないと期限が切れるので、送る直前に発行する運用になる。切れたら発行し直す。
  - ハッシュに salt は付けない。50 ビット弱のコードは DB が漏れれば総当たりで戻せなくはないが、短命・1 回限りで、DB が漏れた時点でデータはすでに見えているため、この用途では十分とする。

## ADR-027: Vercel では `main` を公開用、`develop` をテスト用にし、関数は東京リージョンに置く
- **Status**: Accepted (2026-10-17)。Supabase を分ける部分は ADR-031 で変更
- **Context**: iPhone の PWA（Google ログインから戻れるか、Web Push）は HTTPS でしか確かめられないので、M9 より前に公開 URL が要る。公開する前に同じ構成で確かめる場所も欲しい（オーナーの要望）。Vercel の既定では関数が米国東部で動き、東京の Supabase と往復するたびに遅くなる。Hobby の Preview の URL は既定で Vercel のログインで保護されている。
- **Decision**:
  - `main` を Vercel の Production（公開用）、`develop` を Preview（テスト用）にする。作業ブランチ → `develop` でテスト用 URL（`develop` に割り当てた `force-study-app-staging.vercel.app`）に出し、確かめてから `develop` → `main` で公開する。
  - Deployment Protection の Vercel Authentication はオフにする（iPhone のホーム画面アプリから開けるように）。アプリは Google ログインと招待コードで守る。
  - Supabase は、M9 まで両方とも開発用プロジェクトにつなぐ。M9 で本番用プロジェクトを作ったら、Production の環境変数だけを差し替える。
  - `vercel.json` の `regions` を `hnd1`（東京）にする。`package.json` の `engines` で Node 22 以上を指定する。
- **Consequences**:
  - 公開している版は `main`、確かめている版は `develop` で分かる。iPhone ではいつも同じテスト用 URL で試せる。
  - M9 までは公開用 URL も開発中のデータと同じ DB を使うので、メンバーへの本格的な案内は M9 のあとにする。
  - M9 以降は、テスト用（開発用 Supabase）と公開用（本番用 Supabase）でデータが分かれる。定期実行（pg_cron → `/api/cron/tick`）も、各 Supabase プロジェクトが自分の環境の URL を呼ぶ。

## ADR-028: 通知の配信の作り（M3）
- **Status**: Accepted (2026-10-17)
- **Context**: M3 で `activity_events` → `notifications` → Web Push の配信と、通知ゲート（F0）を作る。CLAUDE.md の「通知は `activity_events` に書いて `lib/notify` に渡す」を守りつつ、F0 のテスト通知のようにタイムラインに出さない Push もある。
- **Decision**:
  - 受信者と文言はイベントの種類ごとのルール（`lib/notify/rules.ts`、純粋な関数）で決め、DB は `create_notifications` で記録するだけにする（受信者ルールは TypeScript でテストしやすく、DB は冪等さと「抜けた人に送らない」を守る）。
  - 呼び出し側は RPC でイベントを記録したあと、`after()` の中で `dispatch(eventId)` を呼ぶ。配信の失敗はログだけで、元の操作は失敗させない（通知はアプリ内の一覧に残る）。
  - F0 のテスト通知だけは `activity_events` を通さず、`lib/notify` の `sendTestPush` がその端末にだけ送る。Server Action から直接 web-push を呼ばない、というルールは保つ。
  - 端末（endpoint）は 1 人に属する。同じブラウザで別の人がログインして登録したら、その人に移して確認をやり直させる。
  - 未読数は下部メニューの「通知」タブのバッジで見せる（ヘッダーのベルは置かない。画面が狭く、下部メニューに通知タブがあるため）。
  - `VAPID_SUBJECT` は公開用の `https://` URL にする（個人のメールアドレスを Push サービスに渡さない）。
- **Consequences**: 新しい通知は `rules.ts` にルールを足すだけで、配信・Push・既読は共通になる。M6 の cron は、`pushed_at` が null の通知を送り直す処理を足せる。

## ADR-029: ルールの「現在時刻」は `private.now()` にまとめ、テストで固定できるようにする
- **Status**: Accepted (2026-10-17)
- **Context**: 宣言締切（12:00）・提出締切（21:00）・指摘の 3 時間・書き直しの 1 時間・休会の 23:59 など、M4 以降のルールはほとんどが時刻で決まる。DB のテスト（PGlite）を実行した時刻によって結果が変わると、テストが壊れやすい。
- **Decision**: RPC が使う現在時刻は `private.now()`（ふだんは `now()`）にまとめ、`jst_today()` もこれを使う。テストのセッションだけ `set app.now = '...'` で固定する（`tests/db/harness.ts` の `setNow`）。行の `created_at` などの既定値は `now()` のまま。
- **Consequences**: 時刻に関わるルールを、決まった日時で再現性よくテストできる。`app.now` を設定できるのは SQL を直接実行できる人だけで、API からは設定できず、RPC も `service_role` だけが呼べるので、本番で時刻をずらされることはない。

## ADR-030: AI 判定は Route Handler ではなく Server Action から呼ぶ
- **Status**: Accepted (2026-10-17)
- **Context**: 設計では、ブラウザが提出を記録したあと `/api/judge` に POST して判定する予定だった。Route Handler にすると、ログインと本人確認を自前で書く必要がある。
- **Decision**: 判定の本体は `lib/judging.ts` の `judgeSubmission(submissionId)`（写真を Storage から取得 → Gemini → `record_judgement`、失敗したら `record_judge_error`）。ブラウザは Server Action `judgeMySubmission` を呼び、そこで本人の提出かを確かめてから実行する。M6 の cron tick も同じ関数で `error` の提出を判定し直す。写真の入力は `capture` 属性を付けず、端末の「カメラで撮る / 写真を選ぶ」の選択に任せる（`capture` を付けるとギャラリーから選べない端末があるため）。
- **Consequences**: 認証は Server Action の仕組み（Origin の確認と Cookie のセッション）に乗る。判定は数秒〜数十秒かかるので、その間ボタンを「AI が判定中…」にする。途中で画面を閉じても提出は記録済みで、「もう一度判定する」で続きができる。

## ADR-031: Supabase は 1 つのプロジェクトを本番とテスト用で共有する
- **Status**: Accepted (2026-10-18)。ADR-024 と ADR-027 の「M9 で本番用プロジェクトを分ける」を置き換える
- **Context**: Supabase の無料プロジェクトは、Owner・Admin になっている organization 全部で同時に 2 つまで。もう 1 つの枠はオーナーの仕事で使っている。有料プランは使わない（ADR-003）。
- **Decision**:
  - 今のプロジェクト（`nvckqojuwkelguayshta`。organization `force-study-app`、Tokyo）を本番として使い、公開用（`main`）もテスト用（`develop`）もローカル開発もここにつなぐ。
  - 定期実行（pg_cron の `tick_url`）は公開用の URL を呼ぶ。テスト用は呼ばない（1 つの DB に対して tick は 1 か所）。
  - マイグレーションは `develop` にマージする前に適用されるので、**公開中の `main` の古いコードでも動く形**（列・関数の追加だけ、既存の引数や戻り値を変えない）にする。ルールの確認は PGlite のテストで済ませる。
  - 仲間を招待する前に残っているテストのデータは、必要なら一度だけ消す（`supabase db reset --linked`）。仲間が参加したあとは使わない。
- **Consequences**:
  - テスト用 URL やローカルで操作すると、本物の記録として残る（記録は消せない。ADR-020）。テスト用 URL は新しい画面の表示確認に使い、ためしの宣言・提出・ペナルティは作らない。
  - 環境変数は Production・Preview・ローカルで Supabase の値が同じになる。
  - 無料枠（DB 500MB・Storage 1GB）は 1 つ分だけで足りる見積もり（architecture.md §6）。
  - 将来、無料の枠が空いたら本番用を分けられる。そのときは Production の環境変数と `tick_url` を差し替える。

## ADR-032: 提出は次の日の宣言の締切まで。次の宣言は前の日を片付けてから
- **Status**: Accepted (2026-10-18)。要件の「その日の締め」（その日のうちに決着させる）を置き換える
- **Context**: 夜中に勉強したい日もある（オーナーの要望）。提出締切を当日 21:00 までにすると、深夜の勉強が数えられない。一方で、締切を延ばすと「いつまでも決着しない日」ができる。
- **Decision**:
  - 提出締切は宣言したときに **次の日の宣言の締切（`declaration_cutoff`、既定 12:00）** に自動で決まる。本人が締切を選ぶのはやめる（`declare_goal` の `p_end_time` は互換のために残して無視する）。
  - 次の日の宣言は、前の日が **合格している** か、**未達成で理由を申告済み** でないとできない（`declare_goal` が `previous_day_open` / `previous_report_due` を返す）。勉強できなかった日は、本人が「**できなかった**」（RPC `give_up_day`）を押して未達成にし、理由を申告する。
  - 理由申告の期限は、学習日の翌日の `report_deadline`（23:00）。「怪しい」は合格した提出から `dispute_window_hours`（24 時間）、送り直しは最初の「怪しい」から `resend_minutes`（24 時間）、理由の審査と「怪しい」の最終審査は始まってから `review_hours`（24 時間）。休会の審査は申請した日の 23:59 のまま。
  - お試し期間の免除は、ペナルティが決まった時刻ではなく **学習日** で判定する（土曜の分が日曜に決まっても免除）。
  - 精算は土曜 23:59 のまま、その時点で決まっているペナルティだけを入れる。決着していない日の分は、決まったあとの週の精算に入る（学習日で束ねているので自然にそうなる）。
  - 使わなくなった設定（`submit_deadline_max`・`dispute_cutoff`・`resend_cutoff`）は列を残して画面から外す（マイグレーションは追加だけ）。
- **Consequences**:
  - 夜中の勉強も数えられる。朝は「昨日の分の提出」と「今日の宣言」が並ぶので、ホームの「やること」と通知で前の日を先に済ませるよう案内する。
  - 何もしないで次の日の 12:00 を過ぎると、前の日は未達成（理由申告がなければ P5）、その日は宣言なし (P1) と、2 日分のペナルティが付きうる。11:00 の通知でそれを伝える。
  - 審査や「怪しい」の期限がどの時刻にもなりうるので、通知と画面の期限は日付つき（「10/21(水) 12:00」）で出す。
  - 1 つの学習日の決着が最大で 2〜3 日かかる。その日が終わるまで、履歴では「進行中」として数える。

## ADR-033: AI が判定できないときは仮合格にして、メンバーが確かめる
- **Status**: Accepted (2026-10-18)
- **Context**: Gemini の無料枠はレート制限や障害で止まることがある。これまでは判定エラーを 5 分ごとに再判定するだけで、AI が戻らないまま締切を過ぎると、提出していても未達成になった。ADR-032 で「合格しないと次の宣言ができない」としたので、AI が止まると提出した人が「できなかった」を押すしかなくなる。AI が動かなくてもアプリは動くようにしたい（オーナーの要望）。
- **Decision**:
  - 通常の提出が、送ってから `ai_fallback_minutes`（既定 30 分）たっても判定されていない（`judging` / `error`）か、その日の提出締切が来たら、定期実行（`pass_unjudged`。締切の処理より先に動く）が **仮合格** にする。点数は付けず、`submissions.unverified_at` に印を付ける。1 日に 1 件（いちばん早い提出）。「軽すぎる」の書き直し待ちのあいだはしない。
  - 仮合格のあとは、ふつうの合格と同じ「怪しい」の窓（`dispute_window_hours`、仮合格の時刻から 24 時間）で、メンバーが写真の合言葉と内容を確かめる。おかしければ「怪しい」→ 送り直し → 最終審査の流れで止める。メンバーには `judged_unverified` で確認を頼む（すぐ対応が要る通知）。
  - あとから AI が答えても、仮合格は変えない（結果が後から変わると混乱する。`record_judgement` は `already_judged` になる）。
  - 不合格の判定が出た提出は対象にしない（AI が動いて落ちたものは落ちたまま）。
- **Consequences**:
  - AI が止まっても、宣言・提出・次の宣言・精算まで止まらない。AI が止まっている間は、チェックがメンバーの目だけになり、ゆるくなりうる。
  - 仮合格の日は点数がないので、平均点の計算からは外れる。

## ADR-034: グループを複数作れるようにする。1 人 1 グループ
- **Status**: Accepted (2026-10-19)。ADR-026 の「最初の 1 人は INVITE_CODE で入る」を置き換える
- **Context**: ほかの人たちもそれぞれグループを作って使いたい（オーナーの要望）。1 人が複数のグループに入り、宣言を共有する形も考えたが、ルール（締切・合格点など）・指摘・審査がグループをまたぐと、結果が 1 つに決まらず、知らない人どうしで審査することになる。
- **Decision**:
  - `groups` を作り、`profiles.group_id`・`group_settings.group_id`（グループごとに 1 行）・`invites.group_id`・`activity_events.group_id` を持たせる。**1 人 1 グループ**で、あとから移れない（`profiles.group_id` は変えない）。
  - まだグループに入っていない人は、招待コードで入るか、`create_group` で新しく作る。作った人が管理者になる。管理者は `set_admin` で増やせて、0 人にはできない。グループ名は `rename_group` で変えられる。
  - RLS は「自分のグループの行だけ」にする（`private.my_group()`）。Storage の証拠写真も同じグループだけ。RPC はその人のグループの設定で動き、相手が同じグループかを確かめる。時刻で動く定期実行はグループごとに回す。通知はイベントのグループのメンバーにだけ送る。
  - 無料枠（Storage 1GB・Gemini の回数）はアプリ全体で共有するので、`app_limits`（既定: 10 グループ・合計 50 人）で上限を置く。
  - 既存のメンバーは「Commit or Treat」という 1 つ目のグループにまとめる。`INVITE_CODE` はグループが 1 つもないときだけ使える。
- **Consequences**:
  - グループごとにルール・お金・タイムラインが分かれる。公開中の古いコード（ADR-031）は、2 つ目のグループができるまではそのまま動く（設定は RLS で 1 行に見え、通知の相手も 1 グループだけ）。
  - グループを抜けて別のグループに移る機能はない。必要になったら、記録の行にグループを刻む形（参加履歴）に広げる。
  - 1 人が複数のグループに入る形（宣言の共有）は作らない。

## ADR-035: profile を「1 回の所属」にして、退会と入り直しをできるようにする
- **Status**: Accepted (2026-10-19)。ADR-034 の「1 人 1 グループで、あとから移れない」を「同時に 1 つ」に変える
- **Context**: テストアカウントを外したい。退会したあと、同じアカウントで別のグループ（同じグループでもいい）に入れるようにしたい。管理者が人を外す機能も欲しい（オーナーの要望）。これまで profile の id はアカウントの id と同じで、記録（宣言・ペナルティなど）はすべてこの id を指していたので、別のグループに入り直すと前のグループの記録まで付いてきてしまう。
- **Decision**:
  - profile を「1 回の所属」にする。id はアカウントとは別に作り（既存の人はアカウントの id のまま）、`auth_user_id` でアカウントを指す。有効な所属はアカウントごとに 1 つ（部分一意インデックス）。記録の表はそのままで、所属ごとの id を指すので、入り直すと新しい id で記録が始まり、前の記録は前のグループに残る。
  - ログイン中の人の判定（RLS の自分の行・通知・端末・写真のフォルダ、サーバーの `getMember`）は `private.my_member()` / `auth_user_id` で、今の有効な所属を引く。
  - 退会（`leave_group`）は、お金と終わっていない日を片付けてから。管理者が外す（`remove_member`）のは、それらが残っていてもできる。どちらも記録は消さない。外された人の終わっていない日はペナルティなしで閉じ、退会した人にはペナルティを付けない。
  - 2 回目以降の所属にはお試し期間を付けない（退会と入り直しを繰り返して無料期間を延ばせないように）。
- **Consequences**:
  - グループを移っても、前のグループの記録と新しいグループの記録が混ざらない。振り返りは所属ごと（前のグループの記録は、新しいグループからは見えない）。
  - 入り直した人は、通知の設定（F0）もやり直す（端末は新しい所属に付け替わる）。
  - 公開中の古いコードは「profile の id = アカウントの id」を前提にしているので、この変更のあとに新しく入った人は古いコードではメンバーと見なされない。DB の変更と同時に main へ出す。

## ADR-036: ほかのアプリを使えなくするペナルティは作らない
- **Status**: Accepted (2026-10-18)
- **Context**: お金以外のペナルティとして、Instagram や YouTube を見られなくしたい（オーナーの要望）。
- **Decision**: アプリを止める形のペナルティは作らない。理由:
  - PWA（ブラウザ）から、ほかのアプリを止める API は iOS にも Android にもない。
  - iOS のスクリーンタイム API（Family Controls）はネイティブアプリと Apple Developer の登録（年 $99）が要り、0 円運用 (ADR-003) に反する。Android のネイティブアプリなら作れるが、本人がアンインストールすれば終わる。
  - YouTube・Instagram の設定（休憩のリマインダー・利用時間の上限など）は通知が出るだけで見られなくはならず、外から変える公式の API もない。本人の Google アカウントのログイン情報を預かって自動で操作するのは、規約違反・アカウントのロック・漏れたときの被害が大きすぎる。
  - 「禁止令 + 使用時間のスクショで証明」も考えたが、PC や別の端末で見られ、強制力が弱い。
- **Consequences**: お金以外のペナルティは、アプリの中で確かめられる「補習」と、アプリの中で強制できる「称号・ランク」にする (ADR-037)。

## ADR-037: サボりが続いたら補習を科し、称号と XP のランクを付ける
- **Status**: Accepted (2026-10-18)。ランクを決める XP の範囲は ADR-039 で直近 28 日に変えた
- **Context**: ペナルティがお金だけだと、払えば済んでしまう。学習アプリなので、失敗した分を学習で取り返させたい。良い成果にも目に見えるごほうびがあると続けやすい（オーナーの要望）。
- **Decision**:
  - **補習**: サボり（P1・P2・P5・P6）が 3 回連続になったら、3 回目から 1 回ごとに補習 1 回を科す (P9)。毎回のペナルティに付けると重すぎるので、サボりが続いたときだけ効くブレーキにする（P3 の「4 回連続から」と同じ形）。補習 1 回は普段の 1 日分と同じ流れ（宣言・合言葉・AI 判定・「怪しい」）で確かめる。期限は翌週の土曜 23:59 で、返しきれなければ P10 で +1 回ずつ繰り越す（お金の P7 と同じ考え方）。補習の失敗そのものにはペナルティを付けない（借りが減らないだけ）。
  - **称号**: 悪い称号（未達の王・サボラー・逃走者・貧乏人など）と良い称号（皆勤賞・無課金勢など）を、状態・今月の回数・連続・週の締めの条件で自動で付ける。回数で付く悪い称号は月が変わったらリセットする（反省すれば消える）。「奢り確定」バッジは「貧乏人」に置き換える。
  - **XP とランク**: 全員 0 XP（三日坊主）から始め、達成で増え、ペナルティで減る。5 段階のランクと、グループ内の順位（1 位に王冠・最下位はカードが傾く）で見た目を変え、全員から見えるようにする。
  - **称号と XP は保存せず、記録から計算する**（カウンター列を作らない。ADR-005 と同じ）。付いた・外れた・変わったという出来事だけを `activity_events` に書き、そこから通知する（`lib/notify`）。
  - 「貧乏人」は、期限を過ぎて P7 が付いた精算がある人にだけ付ける（期限内に払う人まで毎週「貧乏人」にしない）。
  - **数字の単位を分ける**: 画面では「pt」を使わず、お金は「円」、補習は「回」、ランクは「XP」で出す。ペナルティと XP の 2 つの数字が混ざらないようにするため。データの列名はそのまま。
  - 称号の条件・XP の増減・ランクの区切りはアプリ共通にする（グループで変えると、称号の意味がグループごとにずれる）。P9 の連続回数と補習の回数は、お金と同じくグループ設定で変えられる。
- **Consequences**:
  - 補習が付くのはサボりが続いたときだけなので、ふだんの重さは今と変わらない。
  - 補習のための宣言・提出が増えるので、Gemini の呼び出しと Storage が増える（1 日 1 回までなので、増えても今の 2 倍以内）。
  - 称号と XP を毎回計算するので、ホームを開くたびの集計が重くなる。重ければビューにまとめるか、画面側でまとめて計算する。
  - 見た目が悪くなるのは飾りだけにして、読みやすさと操作は変えない（罰で学習できなくなったら本末転倒）。
  - バッジのイラストはオーナーが描く。届くまでは仮の絵で動かす。

## ADR-038: はじめての体験は「入口の案内 → 必須のレクチャー → その場面のコーチマーク」で作る
- **Status**: Accepted (2026-10-18)
- **Context**: これまでの案内は、ログイン前に読む `/guide` だけだった。参加するといきなり「今日の宣言」が出て、お金が絡むルールに同意する場面がない。合言葉の写し方は最初の提出で初めて知ることになる。招待リンクを LINE で開くと、LINE の中のブラウザで Google がログインを拒否し、最初の一歩で止まる。ログインしたら、これからどう使えばいいかを簡単にレクチャーしたい（オーナーの要望）。
- **Decision**:
  - **入口**: 招待リンクに `openExternalBrowser=1` を付け、`/login` で User-Agent からアプリの中のブラウザを見分けて、Safari / Chrome での開き直しを案内する。見分けられないアプリもあるので、文言でも伝える。
  - **レクチャー「はじめに」**: グループに入った直後、通知の設定 (F0) より前に、横にめくるカード 6 枚を見せる。**飛ばせない**。最後の「このルールで始める」を同意とし、押した時刻を `profiles.rules_accepted_at` に残す。お金が絡むので、全員が一度は全部見たことにしたい。1 分程度なので負担は小さい。数字はそのグループの設定と本人のお試し期間を出す。F0 より前に置くのは、「締切は通知でしか届かない」と分かってから通知の設定に進んでもらうため。
  - **コーチマーク**: レクチャーで全部を覚えさせようとせず、宣言した直後の合言葉・最初の提出・初めての指摘や審査など、その場面に初めて来たときに 1 つだけ吹き出しを出す。最初に画面をまとめて案内するツアーは作らない（参加した直後のホームはほとんど空で、大事な場面はあとからばらばらに来るため）。
  - **既読は DB に覚える**（`profiles.seen_tips`）。iPhone では Safari とホーム画面のアプリで保存場所が別で、PC とスマホを両方使う人もいるので、端末に覚えると同じ説明が何度も出る。書き込みは Server Action → RPC にする（ADR-004）。
  - **今いるメンバーには出さない**: マイグレーションで `rules_accepted_at` を埋め、`seen_tips` を `'*'`（全部見た）にする。グループに入り直した人には、ルールが違うかもしれないのでレクチャーは出し、コーチマークは出さない。
  - iPhone は今の順番（Safari で参加 → ホーム画面に追加 → アイコンから開いてもう一度ログイン）のままにし、2 回目のログインが要ることを先に書いておく。先にホーム画面に追加させるとログインは 1 回で済むが、アイコンから開くと招待コードが URL から消えて入れ直しになる。
- **Consequences**:
  - ゲートが 2 段（レクチャー → 通知）になる。どちらも `(app)` の外の画面で、`(app)/layout.tsx` がこの順に確かめる。
  - ルールが変わっても同意は取り直さない。取り直しが要るほど変わったら、`rules_accepted_at` を空にするマイグレーションで全員にもう一度見せられる。
  - コーチマークを足すときは、キーをコードの定数に足すだけで DB は変えない。

## ADR-039: ランクと王冠は直近 28 日の XP で決める
- **Status**: Accepted (2026-10-18)。ADR-037 の「XP を積み上げてランクを決める」を置き換える
- **Context**: XP をずっと積み上げてランクを決めると、週 6 日宣言・失敗はサボりとして計算した場合、次のことが起きる。
  - 3 か月完璧だった人（約 1,200 XP）は、そのあと週 3 日サボっても天才を下回るまで約 15 週かかる。今サボっているのに金の枠のまま。
  - 王冠は早く始めた人が持ち続け、あとから入った人は追いつけない。
  - 週 1 日サボる程度の人でも半年で天才になり、長く使うほどランクの差がなくなる。
  - 「宣言が妥当じゃなかった」（P3）は 3 回連続まで XP が減らないので、失敗のたびに選べばランクを守れる。
- **Decision**:
  - ランク・王冠・最下位の傾きは、**直近 28 日の XP** で決める。休会の日は 28 日に数えず、そのぶんさかのぼる。
  - 28 日で取れる XP は最大でも約 400 なので、区切りを どうしようもない −50 以下 / 三日坊主 −49〜49 / やればできる 50〜149 / 優等生 150〜299 / 天才 300 以上 にする。
  - P3（3 回連続まで）も −5 XP にする（お金は 0 円のまま）。
  - 積み上げた XP は「通算 XP」としてプロフィールと振り返りに残す（ランクには使わない）。
- **Consequences**:
  - 今の調子がランクに出る。サボり始めたら 1〜2 週間で落ち、あとから入った人も 4 週間で並べる。
  - 何もしなくても、古い達成が 28 日から外れると XP が減り、ランクが下がることがある（そのときも「ランクが下がった」を通知する）。
  - 区切りは仮の値。使ってみて直す（requirements の未決事項）。

## ADR-040: 補習は学習日の表の行として持ち、管理者がオンにした日から数える
- **Status**: Accepted (2026-10-18)
- **Context**: 補習（ADR-037）は 1 回ごとに宣言・合言葉・提出・AI 判定・「軽すぎる」・「怪しい」を通す。これらはすべて `study_logs` の id にぶら下がっている。また、P9 は学習日の履歴を数えるので、そのまま入れると機能ができる前のサボりにもさかのぼって借りが付き、画面がないまま P10 で増えていく。
- **Decision**:
  - 補習 1 回を `study_logs` の `is_makeup = true` の行にする。提出・判定・「怪しい」・最終審査・写真の保存はそのまま使い、学習日を数える処理（宣言・締め・前の日の片付け・P3・`daily_history`・週の振り返り）だけが補習の行を外す。1 日 1 件の一意制約は、学習日と補習で別の部分一意インデックスにする。
  - 補習の失敗（期限切れ・「できなかった」・書き直しなし・証拠不認定）は記録だけで、ペナルティにしない（`add_penalty` が補習の行を無視する）。
  - 借りは `penalties` に混ぜず、別の台帳 `makeup_debts` に置く（お金が 0 円で、P9 は同じ日の P1 などに重なるため）。
  - グループ設定 `makeup_since` が空のあいだは P9 を付けない。管理者が設定で「補習を使う」をオンにした日から数える。
- **Consequences**:
  - 補習の画面は、今の提出・記録の画面をほとんどそのまま使える（`/submit?makeup=1`・`/logs/[id]`）。
  - 公開中の古いコードは「1 人 1 日 1 行」と思って `study_logs` を読むので、補習を宣言できるコードと DB の変更は一緒に main へ出す。`makeup_since` が空なら、DB だけ先に入れても何も起きない。
  - 学習日を読む新しい処理を書くときは、`is_makeup = false` で絞るのを忘れないこと。

## ADR-041: 称号と XP はアプリで計算し、変わったことだけを tick のあとに記録する
- **Status**: Accepted (2026-10-18)
- **Context**: 称号（F13）は 21 種類あり、今月の回数・連続・週の締め・状態と条件がさまざま。XP（F14）は直近 28 日の窓（休会の日を飛ばす）で数える。どれも記録から決まるので保存はしない（ADR-005・ADR-037）。ただ、「付いた・外れた・ランクが変わった・王冠が移った」を通知するには、前の状態と比べる必要がある。
- **Decision**:
  - 計算は SQL ではなく `src/lib/standing/rules.ts`（純粋な関数）で行う。条件が多く、単体テストで確かめやすく、表示にもそのまま使える。読み込みは `load.ts`（RLS 越し。tick は admin でグループごと）。API の 1000 行の上限を超える表はページに分けて読む。
  - 5 分ごとの tick の Route Handler が、DB の tick のあとでグループごとに計算し、前回の `standing_snapshot` と比べて違えば `record_standings` で新しいスナップショットと変化のイベントを記録して通知する。スナップショットは「比べるための記録」で、称号やランクの正本ではない（画面は毎回計算する）。
  - 初めて動いたとき（スナップショットがない）と、スナップショットにいない新しいメンバーは、記録だけして通知しない（全員分の「称号が付きました」が一度に届かないように）。お試し期間だけの称号（「本番なら」）は記録しない。
  - 画面全体の見た目は、レイアウトが見ている本人のランクの印（`data-viewer-rank`）を置き、CSS の `:has()` で切り替える。カードはその人のランク（`.rank-card[data-rank]`）。（カードの見た目は ADR-042 で、見ている本人のランクに合わせる形に変えた）
- **Consequences**:
  - 通知は tick の間隔（5 分）だけ遅れる。月が変わって外れる称号なども、次の tick で通知される。
  - 画面を開くたびに、グループの全記録を読んで計算する（6 人・1 年で数千行）。重くなったら、計算に要る期間で絞るか、ビューにまとめる。
  - 定期実行の通知は本番の URL のコードが送るので、通知が届くのは main に出してから。

## ADR-042: ランクの見た目は、見ている本人のランクで画面全体を着せ替える
- **Status**: Accepted (2026-10-20)。ADR-041 の「カードはその人のランク（`.rank-card[data-rank]`）」を置き換える
- **Context**: これまではカードの枠をそのメンバーのランクで変え、画面全体は見ている本人のランクで少しだけ変えていた（天才は金のアクセント、どうしようもないはくすみ）。Claude Design でランク別の見た目を作り直したところ、1 枚の画面に金・銀・コンクリートのカードが混ざると、どれも中途半端で「自分が今どういう状態か」が伝わらなかった。また、カードごとに見た目を変えると、新しい画面のたびに部品ごとの対応が要る。
- **Decision**:
  - **見ている本人のランクで、画面のカード・ボタン・入力欄・タブ・表・レシート・カルテ・タイムライン・下のメニューまで全部を着せ替える**。天才は金、優等生は銀（金より控えめ）、どうしようもないはボロボロ（破れた紙・ひび・汚れ・ガムテープ・アスファルト）。やればできる・三日坊主は今の紙のまま。ほかのメンバーのランクはバッジと王冠で見分ける。
  - 着せ替えは共通の部品に付けた目印（`Sticker` の `data-surface` / `data-shadow`、ボタンの `th-btn-<tone>`、`th-field` など）を、`src/app/rank-themes.css` が `body:has([data-viewer-theme])` で切り替える。画面ごとのコードは変えない。新しい画面も共通の部品を使えば自動で着せ替わる。
  - 破れた紙の縁は `clip-path` で切り、黒い縁取りと影は `filter: drop-shadow` で付ける（`border` は `clip-path` で切れてしまうため）。背景は `::before` に置く。
  - 紙吹雪・キラキラ・ひびの絵は `ThemeLayer`（`components/standing/theme-layer.tsx`）が画面の後ろに固定で置く。素材（粒子・しみ・ひび・テープ・王冠・金のロゴ）は `public/theme/` に置き、合計 300KB 弱にする。
  - 開発中は `/preview` のバーでどのランクの見た目も試せる（`dev_viewer_rank` の cookie。本番では無視する）。
- **Consequences**:
  - 「ランクが下がると自分の画面がボロボロになる」がはっきり伝わる。他人の画面はその人のランクの見た目なので、自分のランクの見た目がほかのメンバーに見えることはない（バッジ・王冠・最下位の傾きは今までどおり全員に見える）。
  - `filter` を付けたカードは、その中の `position: fixed` の基準になる。カードの中にポップアップを置くときは `createPortal` で外に出す（今の「？」とコーチマークはそうしている）。
  - 文字の色は基本的に変えない（濃いインクを明るい面に）。金・銀・ボロボロの画面では赤い文字を濃い赤（`#b3241d`）にし、ボロボロの画面では薄い灰色の文字（`--sub`）を黒に近づける（コンクリートの上で 4.5:1 を保つため）。


## ADR-043: 支払先がそろっていなくてもお試し期間は終える
- **Context**: F8 では「全員の支払先が入力されるまでお試し期間を終えない」としていたが、作っていなかった（支払先のない人の精算は作らずに持ち越し、管理者にだけ通知していた）。お試し期間を延ばすと、支払先を決めないだけで本番が始まらず、ペナルティが付かない抜け道になる。
- **Decision**: お試し期間は支払先と関係なく予定どおり終える。ペナルティはいつもどおり貯まる。支払先のない人の精算は作らずに次の精算へ持ち越し（今の `run_weekly_settlement` のまま）、毎週の締めで**管理者と本人の両方**に `payee_missing` を通知する。本人が管理者なら管理者向けの 1 通だけにする。
- **Consequences**: DB の変更はなく、通知の宛先（`lib/notify/rules.ts`）だけ変わる。支払先が決まった週の精算に、それまでの分がまとめて入る。

## ADR-044: やればできるは銅、三日坊主は少しだらけた紙にする
- **Context**: ADR-042 では天才（金）・優等生（銀）・どうしようもない（ボロボロ）だけを着せ替え、真ん中のやればできる・三日坊主は普通の紙のままだった。けれど全員が三日坊主から始まり、ふだんいちばん長くいるのもこの 2 つで、「いまどこにいるか」「上がると何が変わるか」が画面から伝わらなかった。
- **Decision**:
  - **やればできる = 銅**。金・銀と同じ磨いたカード・ボタン・入力欄（`data-viewer-finish="polished"`）を銅色のパレットで出し、タイトルは金の画像を CSS のフィルターで銅にする。紙吹雪・きらめきは付けない。金 → 銀 → 銅で、上がっていく段が一目でわかる。
  - **三日坊主 = 少しだらけた紙**（`data-viewer-finish="slack"`）。紙とインクはそのままに、大きなカードにうっすら折り目（文字の後ろ）と、右下の角のめくれ（余白の中）、タイトルの角に赤い「坊」のハンコ。どうしようもないのボロボロの手前の空気にする。
  - 濃い赤の文字（`.text-red` を `#b3241d` に）は、紙のままの三日坊主には適用しない。
- **Consequences**: どのランクでも画面が何かしら変わる。三日坊主のめくれは `position: relative` と `::after` を大きなカードに足すので、カードの中に絶対位置の部品を置くときはこの基準になる（ボロボロのカードと同じ）。

## ADR-045: 見た目のテーマを選べるようにし、期間限定のテーマは自動で切り替える
- **Status**: 一部を ADR-046 で変更 (2026-10-20)
- **Context**: Claude Design で、森・海・雪・桜・夕焼け・宇宙と、季節のハロウィン・クリスマス・お正月の見た目を作った（`Theme Picker v4`）。ランクの見た目（ADR-042・ADR-044）は見ている本人のランクで決まり、自分では選べない。同じ画面にランクの見た目とテーマを重ねると、組み合わせが 5 × 9 になり、どちらも中途半端になる。
- **Decision**:
  - **テーマは本人の画面だけ**。`profiles.ui_theme`（null = 標準）と `season_themes` に持ち、`set_ui_theme`（service_role だけ）で書く。テーマの一覧はコード（`src/lib/theme/themes.ts`）が持ち、DB は形だけ確かめる（コーチマークのキーと同じ考え方）。
  - **重ねない**: 標準を選んでいる人だけがランクの見た目。ほかのテーマを選ぶと、ランクの見た目の代わりにテーマになる。ただし**どうしようもないのあいだはコンクリートのまま**（罰の見た目を選んで外せないように）。期間限定のテーマも、どうしようもないには勝たない。
  - 期間（JST の月日、両端を含む）のあいだは、スイッチがオンの人は期間限定のテーマになる。どれにするかは `lookFor`（純粋な関数、単体テスト）が決める。ランクで解放する案（夕焼けは優等生・宇宙は天才）は採らず、全部いつでも選べる。
  - 着せ替えはランクの見た目と同じ目印（`data-surface`・`th-btn`・`th-field`・`th-nav` など）に、`src/app/ui-themes.css` が `body:has([data-ui-theme])` で色・枠・影を当てる。テーマごとの値は `--ui-*` のトークンにまとめ（デザインの値をそのまま移した）、設定画面の見本は `[data-ui-preview]` で同じトークンを使う。
  - 暗い背景のテーマがあるので、文字の色は「背景の上」（`--ui-onbg`）と「面の上」（`--ui-ink`）を分ける。ページで `--ink` を背景用にし、カード・入力欄・レシートなどの面で面用に戻す（`color` は下の layer に置き、`text-red` などのユーティリティが勝つようにする）。小さい明るい色の部品（アバター・ハイライト・赤いカルテ）は濃いインクのまま。
  - 背景の飾り（月とコウモリ・電飾・光の筋・丘とランタン・星座など）は `UiThemeLayer`（`components/theme/ui-theme-layer.tsx`）が画面の後ろに固定で置く。カードの角の飾り（クモの巣・かぼちゃ・ヒイラギ・水引・葉・積もった雪）は CSS の `::before` / `::after` と SVG で描き、画像が届いたら差し替える（`docs/visual-assets.md`）。
- **Consequences**:
  - テーマを選ぶと、標準のランクの見た目（金・銀・銅）は見えなくなる。ランクはバッジ・王冠・振り返りで分かる。
  - 大きなカードは `position: relative` になり、角の飾りに `::before` / `::after` を使う（三日坊主のめくれと同じ）。カードの中に絶対位置の部品を置くときは、カードが基準になる。
  - 新しい画面も共通の部品を使えば自動でテーマになる。`bg-white` や `bg-[#…]` の面を直に書くと、暗いテーマで文字の色が合わないことがあるので、面は `Sticker` などの部品を使う。

## ADR-046: 見た目を選べるのはやめ、期間限定のテーマは仕上がるまで本番に出さない
- **Status**: Accepted (2026-10-20)
- **Context**: ADR-045 で、森・海・雪・桜・夕焼け・宇宙を選べるようにし、ハロウィン・クリスマス・お正月を期間中に自動で切り替えるようにして本番に出した。オーナーが見直して、選べるテーマはやめることにした。期間限定のテーマは残すが、UI がまだ仕上がっていない。本番ではちょうどハロウィンの期間で、メンバー全員の画面がハロウィンになっていた。
- **Decision**:
  - **選べるテーマをやめる**。6 つのテーマの CSS・背景の飾り・設定の「見た目のテーマ」（`/settings/theme`）・`/preview/theme`・Server Action `setUiTheme` を消す。期間外の見た目は、これまでどおりランクの見た目（F14）だけ。
  - **期間限定のテーマは、本番では出さない**。`ViewerTheme` が `VERCEL_ENV === "production"`（Vercel が本番の配信で付ける）のときは季節を見ない。テスト用 URL（Preview）とローカルの開発では今までどおり期間中に出る。コードを develop に残したまま main に出せるので、仕上げの作業を別ブランチに溜めずに済む。
  - 自動の切り替えを止めるスイッチは、UI が仕上がってから置くか決める。それまで設定の画面には何も出さない。
  - DB はそのまま（マイグレーションは追加だけ）。`profiles.ui_theme` と `set_ui_theme` は使わなくなるが残す。`season_themes`（最初はオン）は `lookFor` が読む。
- **Consequences**:
  - テスト用 URL を開くと、期間中はハロウィンなどの見た目になる。本番と見た目が違うのは、このテーマだけ。
  - 本番に出すときは `SEASON_THEMES_LIVE` の条件を外し、F16 と roadmap の M13 を直す。
