# 設計判断の記録 (ADR)

新しい判断は末尾に追記する。考えが変わったときは古い項目を消さず、Status を `Superseded by ADR-xxx` にする。

---

## ADR-001: 通知はアプリ内通知 + Web Push で完結させる
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様は Discord Webhook で晒し上げる設計だった。オーナーの要望は「外部ツールは使いたくない、アプリ内で完結させたい」。
- **Decision**: 通知の正本は DB の `notifications`（アプリ内のベル・一覧。Supabase Realtime で即時反映）。アプリを閉じているときは PWA の Web Push（VAPID + `web-push`）で届ける。晒し上げはダッシュボードのタイムラインで行う。
- **Consequences**:
  - iOS で Push を受け取るには **iOS 16.4 以降でホーム画面に追加**する必要がある。オンボーディングで案内する。
  - Push は届くことが保証されない（OS の省電力機能・通知の拒否）。アプリ内通知を正本にして、Push は「おまけ」として扱う。
  - 外部サービスのアカウントは不要。費用も 0 円のまま。

## ADR-002: Gemini のモデルは環境変数で指定する
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様の `gemini-2.0-flash` は 2026-06-01 に提供終了している。無料枠で使えるモデルやレート制限は頻繁に変わる（2026-04 以降、Pro 系は無料枠の対象外）。
- **Decision**: `GEMINI_MODEL` 環境変数でモデル ID を指定する。既定は無料枠のある Flash 系の最新版（実装時に Google AI Studio で ID を確認する）。SDK は `@google/genai`。出力は `responseMimeType: application/json` + `responseSchema` で `{score, feedback}` に固定する。
- **Consequences**: モデルの提供終了はコードを変えずに環境変数の変更だけで対応できる。判定のたびに使ったモデルを `submissions.ai_model` に残す。

## ADR-003: 定期実行は Supabase pg_cron で行う（GitHub Actions は使わない）
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の仕様は GitHub Actions を 15 分ごとに実行する設計だった。
  - private リポジトリの無料枠は月 2,000 分で、ジョブ 1 回ごとに 1 分単位で切り上げて課金される。15 分ごとだと月 ~2,900 回になり、**無料枠を超える**。
  - public リポジトリなら無料だが、スケジュール実行は数十分遅れることがよくあり、60 日間活動がないと自動で無効になる。
  - Vercel Hobby の Cron は 1 日 1 回まで。
- **Decision**: Supabase Free に含まれる `pg_cron` + `pg_net` で、5 分ごとに `POST /api/cron/tick` を呼ぶ。シークレットは Supabase Vault に置く。
- **Consequences**: リポジトリの公開・非公開に関係なく 0 円で動く。tick は冪等に作るので、取りこぼしや重複があっても問題ない。

## ADR-004: 書き込みはサーバーだけが行い、状態遷移は Postgres 関数に集める
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の RLS では、ユーザーが自分の `total_penalty_points` や `status`・`ai_score` を直接書き換えられた。罰ゲームアプリでは改ざんへの耐性が肝になる。
- **Decision**: `authenticated` ロールに許可する書き込みは、プロフィールの表示項目・通知の既読・自分のフォルダへの画像アップロードだけ。それ以外は Server Action / Route Handler が service role で RPC を呼ぶ。RPC は `service_role` だけが実行できる。
- **Consequences**: 検証ロジックが DB に 1 か所だけになり、cron と画面操作で同じルールが使われる。そのぶん SQL の量は増えるので、pgTAP などで RPC のテストを書く。

## ADR-005: ポイントは台帳で管理する
- **Status**: Accepted (2026-10-16)。ADR-008 で 1 行 = 1pt から 1 行 = 任意の額に、ADR-012 で一意制約を `dedupe_key` に変更
- **Decision**: `profiles` にカウンター列を持たせず、`penalties`（`study_log_id` が unique）から集計する。精算済みかどうかは `settlement_id` で判断する。
- **Consequences**: 二重ペナルティは一意制約で防げる。精算でどの失敗が消化されたかも追える。

## ADR-006: 招待コード + サーバー側でユーザーを作成する
- **Status**: Superseded by ADR-025
- **Decision**: Supabase の公開サインアップは OFF。サインアップ用の Server Action で `INVITE_CODE` を定数時間比較し、通ったら `auth.admin.createUser({ email_confirm: true })` で作る。
- **Consequences**: anon key で Auth API を直接呼んでも登録できない。確認メールを送らないので、Supabase 無料枠のメール送信上限の影響も受けない。

## ADR-007: 日付は JST 固定、締切は提出時刻で判定する
- **Status**: Accepted (2026-10-16)
- **Decision**: 学習日は `(now() at time zone 'Asia/Tokyo')::date`。提出の締切判定は `submissions.submitted_at < target_end_time` で行う（AI 判定がいつ終わったかは問わない）。判定待ちの間は cron が `judge_grace_minutes` だけ失敗の確定を待つ。
- **Consequences**: 締切直前に提出した人が、Gemini の遅延のせいで失敗にならない。

## ADR-008: ペナルティは 1pt = 1 円とし、失敗の種類と理由で額を変える
- **Status**: Accepted (2026-10-16)
- **Context**: 当初の設計は「失敗 1 回 = 1pt、3pt ごとに全員へ 500 円」だった。オーナーの要望は「払う金額とポイントを同じにする」「失敗には理由を書かせ、理由によって扱いを変える」。
- **Decision**: 宣言なし 500pt、サボり 700pt、「宣言が妥当じゃなかった」は次の計画を書けば 0pt（4 回連続から 500pt）、「急遽予定・その他」はほかの全員が納得すれば 0pt（1 人でも拒否、または期限内にそろわなければ 500pt）、申告しなければサボり扱い。未達成の後処理は `failure_reports` と `excuse_reviews` で状態を持つ。金額はグループ設定で変えられる。
- **Consequences**:
  - 「未達成」がすぐにペナルティ確定ではなくなるので、未達成 → 申告待ち → 審査中 → 確定、という状態が増える。期限切れは cron が処理する。
  - 全員一致が必要なので、1 人が審査を放置すると承認されない。審査締切の 3 時間前に、まだ押していない人へリマインドを送る。
  - 「宣言が妥当じゃなかった」を選び続ける逃げ道は、連続回数の上限で塞ぐ。

## ADR-009: 精算は月の最終日に、支払先 1 人へまとめて払う
- **Status**: Superseded by ADR-010（時期）・ADR-019（支払先の決め方）
- **Decision**: 月の最終日の 09:00 に、確定済みの未精算ポイントを人ごとに合計して `settlements` を 1 件作る。支払先は本人があらかじめ決めた人（`profiles.payee_id`）で、未設定ならほかのメンバーからランダムに 1 人選ぶ。送金した側が「送金した」、受け取った側が「受け取った」を押して完了。
- **Consequences**: 送金は 1 人あたり月 1 回で済む。審査中のものなど、その時点で確定していないペナルティは翌月に回る。ランダムの結果は記録し、選び直せないようにする。

## ADR-010: 精算は毎週土曜 23:00 に行う
- **Status**: Accepted (2026-10-16)。時刻は ADR-023 で 23:59 に変更
- **Context**: 月 1 回だと、ペナルティから支払いまでが最大 1 か月空き、痛みが薄れる。
- **Decision**: ADR-009 の仕組み（支払先 1 人、未設定ならランダム、送金した / 受け取った）はそのままにして、締めを毎週土曜 23:00 (JST) にする。休息日の上限を数える週も日曜〜土曜にして、精算と区切りを揃える。
- **Consequences**: 送金は 1 人あたり最大で週 1 回になる。土曜当日の未達成は 23:00 の時点では確定していないことが多く、翌週の分に入る。

## ADR-011: 宣言の軽さはメンバーの指摘で防ぐ
- **Status**: Accepted (2026-10-16)
- **Context**: 宣言の中身に基準がないと、「本を 5 分読む」のような軽い宣言で毎日楽に達成できてしまう。AI によるチェックや最低時間の案もあったが、オーナーはメンバーによる指摘を選んだ。
- **Decision**: 宣言から 3 時間以内なら、ほかのメンバーがコメント付きで「軽すぎる」を押せる。押されたら本人は 1 時間以内に書き直す。書き直さなければ宣言なし (P6, 500pt)。指摘は 1 宣言に 1 回。
- **Consequences**: 宣言の変更不可に例外ができるので、書き直す前の宣言を `original_declaration` に残して、全員に見えるようにする。1 人の指摘で書き直しになるので、身内どうしの信頼が前提になる。

## ADR-012: 精算は相殺せず、未払いには毎週ペナルティを足す
- **Status**: Accepted (2026-10-16)
- **Decision**: A→B と B→A がある週も相殺しない。次の精算までに「送金した」になっていなければ P7 (500pt) を足し、払うまで毎週続ける。P7 は学習日と関係ないので、penalties の一意制約を `study_log_id` から `dedupe_key`（`log:{id}` / `late:{settlement}:{週}`）に変える。
- **Consequences**: 判定は「受け取った」ではなく「送金した」で行う（支払先が確認を忘れたせいで P7 が付かないようにするため）。支払先は「届いていない」を押して `open` に戻せる。

## ADR-013: 長い休みは全員の承認で休会にする
- **Status**: Accepted (2026-10-16)。期間の上限と期限は ADR-014 で変更
- **Decision**: 期間と理由を書いて申請し、ほかの全員が承認したら成立する。審査は理由申告の審査と同じ仕組み（1 人でも却下、または期限内にそろわなければ不成立）。その日が始まる前に承認されていた日だけを休会扱いにする。休会中の人は審査者から外す。
- **Consequences**: 「全員一致」の審査に参加する人数が日によって変わるので、審査の行は申請・申告した時点で作って固定する。

## ADR-014: 期限を 5 時間に縮め、通知は双方向・期限の手前にも出す
- **Status**: Accepted (2026-10-16)。理由申告・審査の期限は ADR-017 で「次の宣言締切」に変更
- **Decision**:
  - 1 日の始まりは 0:00 JST に固定する（個人ごとの設定はやめる）。0:00 と 11:00 に未宣言のリマインドを出す。
  - 理由申告と審査（理由・休会）の期限は 5 時間。指摘できるのは宣言から 3 時間、書き直しの期限は 1 時間。
  - 休会の長さに上限は設けない。妥当かどうかはほかのメンバー全員の承認で決める。
  - 通知は「行動した人 → 関係する人」「反応した人 → 行動した人」の両方向に出す。期限があるものは、発生時と期限の手前（残り 1 時間・15 分）に出す。自分の対応が必要な通知は Push を OFF にできない。
- **Consequences**: 期限が短いので、Push が届かないと不利になる。通知を許可していない人には警告を出し続ける。夜間に期限が来る問題が残る（requirements §7 の未決事項）。

## ADR-015: 証拠は「合言葉・開始時の写真・使い回し検出・メンバーの指摘」の 4 重にする
- **Status**: Superseded by ADR-016
- **Context**: 写真 + 振り返り + AI 採点だけだと、昔の写真やネットの画像の使い回しを見抜けず、「今日やった」証明にならない（画像は圧縮で撮影日時の情報が消える）。
- **Decision**:
  - 宣言時にその日だけの**合言葉**を発行し、開始時の写真と提出写真の 1 枚以上に写させる。Gemini が確かめ、写っていなければ不合格。
  - **開始時の写真**で学習中になる。開始していないと提出できない。経過時間は全員に見せ、AI の判定材料にもする。
  - **知覚ハッシュ**をサーバー（`sharp`）で計算し、グループ全員の過去の画像とほぼ同じなら Gemini に送る前に不合格。ハッシュは画像を消しても残す。
  - AI が合格にしても、ほかのメンバーが 3 時間以内に**「怪しい」**を押せる。本人は 1 時間以内に追加の証拠を出せ、全員の納得がなければ P8 (700pt)。
  - 審査が 3 種類（理由・休会・疑義）になったので、審査テーブルを `peer_reviews` 1 つにまとめ、`cast_review` で共通に扱う。
- **Consequences**: 依存に `sharp` が増える（Vercel でそのまま動く）。Gemini の呼び出しは開始時の確認ぶん増えるが、1 日 30 回程度で無料枠に十分収まる。合言葉を紙に書く手間が毎日発生する。

## ADR-016: 証拠は「合言葉 + AI 判定 + メンバーの『怪しい』」にする
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-015 の開始時の写真と知覚ハッシュは、オーナーの判断で不要になった。合言葉はその日にならないと分からないので、昔の画像や他人の画像の使い回しは合言葉だけで防げる。
- **Decision**:
  - 提出写真の 1 枚以上に合言葉を写し、Gemini が探す。合格 = 70 点以上 かつ 合言葉あり。合言葉は全員に見えてよい。
  - 合格の通知から 3 時間、ほかのメンバーは「怪しい」を押せる（複数可）。誰も押さなければそのまま達成で確定。
  - 押されたら、本人は 1 時間以内なら何度でも証拠を送り直せる。指摘した全員が取り下げれば確定。そろわなければメンバーの最終審査になり、理由付きの却下が 1 人でもあれば P8 (200pt)。
  - 宣言から提出までの経過時間は見せるだけ（最低時間なし）。
- **Consequences**: `sharp` と開始時の写真が不要になり、実装が軽くなる。最終審査は「期限までに却下がなければ承認」で、理由申告の審査（期限までに全員の納得がなければ却下）と逆の扱いになる。却下に理由を必須にしたため、黙っていることは却下にならない、という整理。

## ADR-017: 理由申告・審査の期限は「次の宣言締切」にする
- **Status**: Superseded by ADR-022
- **Context**: 5 時間の期限だと、夜中に期限が来て寝ている人が押せずに却下・ペナルティになる抜け穴（不公平）があった。
- **Decision**: 理由申告・理由の審査・休会の審査・「怪しい」の最終審査の期限を、出来事のあとに来る最初の 12:00 にする（残り 6 時間未満なら翌日の 12:00）。発生時・8:00・11:00・11:45 に未対応の人へ通知する。提出締切の上限も翌日 12:00 にする。
- **Consequences**: 期限が必ず昼になり、全員が起きている時間に対応できる。期限の計算は `next_deadline()` にまとめる。

## ADR-018: 通知を ON にしないとアプリを使えなくする
- **Status**: Accepted (2026-10-16)
- **Decision**: 全画面の手前に通知ゲートを置き、ホーム画面追加（iOS）・通知の許可・Push 購読・テスト通知の確認（バナーとサウンド）がそろうまで先へ進めない。開くたびに再確認する。通知の種類ごとの OFF はなくす。
- **Consequences**: OS 側のバナー・サウンドの設定は Web から検出できないので、本人によるテスト通知の確認で代える。

## ADR-019: 支払先はグループで決めて管理者が入力する。最初の週はお試し期間
- **Status**: Accepted (2026-10-16)
- **Decision**: 支払先のランダム選択をやめ、グループで話し合って決めた「誰が誰に払うか」を管理者が入力する。全員分そろうまでお試し期間を終えられない。登録から次の日曜 0:00 まではお試し期間で、ペナルティは記録だけして（`waived = 'trial'`）精算しない。パスワードを忘れたら管理者が仮パスワードを発行する。
- **Consequences**: 途中参加のメンバーにも、それぞれお試し期間が付く。

## ADR-020: 記録は追記だけにして、振り返り機能を持つ
- **Status**: Accepted (2026-10-16)
- **Context**: オーナーの要望は「いつ何を宣言し、何を学び、どれだけ達成できたか、却下された理由まで全部残して振り返りたい」。
- **Decision**:
  - 履歴のテーブルは追記だけにする（DELETE 禁止、UPDATE は状態と時刻の列だけ、をトリガーで強制）。外部キーは cascade しない。抜けたメンバーは `deactivated_at` で無効にするだけ。
  - 写真の原寸は 60 日で消すが、サムネイル（~20KB）は永久に残す。文字の記録はすべて永久。
  - 振り返り画面（カレンダー・1 日のタイムライン・統計・指摘と却下の一覧・次の計画の追跡・検索）と、毎週土曜の週の振り返り（数字 + Gemini の要約 + 本人のメモ）、CSV / JSON の書き出しを作る。
- **Consequences**: 間違ったデータを直すときもマイグレーションで明示的に行うことになる（アプリからは消せない）。DB の容量は数 MB/年、サムネイルは ~45MB/年で、無料枠に何年でも収まる。週の振り返りの Gemini 呼び出しは週 6 回程度増えるだけ。

## ADR-021: 振り返りは表とグラフで見せる（shadcn/ui Chart + TanStack Table）
- **Status**: Accepted (2026-10-16)
- **Decision**: 個人の振り返り（数字のカード・達成カレンダー・達成率・点数・時間・時間帯・ペナルティ・未達成理由・指摘と却下・学習ログの表）と、グループの比較（比較表・グループのカレンダー・達成率の比較・ランキング）を作る。グラフは shadcn/ui の Chart（Recharts）、表は TanStack Table、カレンダーは CSS Grid。集計は DB のビューで行う。
- **Consequences**: どれも無料のライブラリで、追加の費用はない。色は 1 か所で管理し、色だけに頼らず記号とラベルを付ける。

## ADR-022: その日の出来事はその日のうちに決着させる
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-017 の「次の宣言締切（翌日 12:00）」は夜中の期限を避けられるが、オーナーの考えは「その日の振り返りはその日にする」。
- **Decision**: 理由申告は当日 23:00、審査（理由・休会・「怪しい」の最終審査）は当日 23:59 まで。そのぶん時間を残すため、提出締切の上限を当日 21:00、「怪しい」の受付を最長 22:00、送り直しを最長 23:00 にする。期限の計算は `day_at(学習日, 時刻)` にまとめる。「怪しい」の最終審査は、23:59 までに理由付きの却下がなければ達成で確定（オーナー確認済み）。
- **Consequences**: 学習日をまたぐ状態がなくなり、日ごとの記録が 23:59 で必ず確定する（振り返りの集計も単純になる）。夜型の人は提出締切を 21:00 より遅くできない。審査者は夜（22:00〜23:59）に対応する必要がある。

## ADR-023: 精算と週の振り返りは土曜 23:59、その日の決着のあとに行う
- **Status**: Accepted (2026-10-16)
- **Context**: ADR-022 で毎日 23:59 にその日の出来事が決着するようになったが、精算が土曜 23:00 だと土曜の分が翌週に回っていた。
- **Decision**: 精算と週の振り返りを土曜 23:59 にし、同じ tick の中でその日の決着を先に済ませてから行う。
- **Consequences**: 1 週間（日〜土）の出来事がすべてその週の精算に入り、持ち越しがなくなる。実際の処理は日曜 0:00〜0:05 の tick で行われる。お試し期間の終わり（日曜 0:00）とも区切りがそろう。

## ADR-024: 開発はクラウドの Supabase 開発用プロジェクトで行う
- **Status**: Accepted (2026-10-16)
- **Context**: ローカルの Supabase は Docker で 10 前後のコンテナを動かし、開発機（メモリ 8GB）には重い。
- **Decision**: Supabase の無料プラン（2 プロジェクトまで）で、開発用と本番用のプロジェクトを分ける。開発中は開発用プロジェクトに直接つなぎ、マイグレーションは `supabase db push` で反映する。キーは新形式（publishable / secret）を使う。
- **Consequences**: Docker が不要。オフラインでは開発できない。データを作り直すときは `supabase db reset --linked`（開発用プロジェクトだけに使う）。7 日使わないと一時停止するので、再開してから作業する。pg_cron から開発機の tick は呼べないので、開発中は tick を手動で呼ぶ。

## ADR-025: ログインは Google、メンバーになるには招待コード
- **Status**: Accepted (2026-10-16)
- **Context**: メール + パスワードだと、パスワードの管理とリセット（Supabase 無料枠のメール送信上限が厳しい）が手間になる。オーナーの提案で Google ログインにする。
- **Decision**: Supabase Auth の Google プロバイダー（OAuth / OIDC、PKCE）でログインする。Google でログインしただけではメンバーにせず、`/join` で招待コードを入れた人だけに profile を作る（`join_group`）。RLS は `private.is_member()`（profile があり抜けていない）で判定する。
- **Consequences**:
  - パスワードとリセットの仕組みが要らなくなる。費用は 0 円（Google の OAuth クライアントは無料）。
  - 招待コードを知らない人も auth のユーザーとしては登録されるが、何も読めない。
  - Google Cloud での OAuth クライアントの作成と、Supabase での設定が初回だけ必要（README）。
  - iPhone の PWA で OAuth から戻れるかは実機で確認する（M2）。だめならメールのワンタイムコードを予備にする。
